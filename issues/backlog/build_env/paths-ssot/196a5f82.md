# title
언어 중립 경로 SSOT(cores/common/paths.ini)와 Rust·Python 극고속 상수 생성

# pre-condition
- 선행: build_env/repo-layout/d9be0edb (목표 구조로 이동 완료)

# steps
근거: 사용자 요청 (2026-10-01): `cores/common/`에서 언어와 무관한 공통 항목(경로 등)을 SSOT로 관리, Rust·Python 모두 가장 빠른 형태로 변환해 호출, Python은 별도 `paths.py`를 만들지 않음. 측정: `ref/actual/logs/paths-bench.log`
1. `cores/common/paths.ini`를 만든다. 형식은 `KEY=루트 기준 상대경로`, `/` 구분, 치환 없음, `#` 주석.
2. Rust: `cores/rust/common/build.rs`가 `paths.ini`를 `OUT_DIR/paths.rs`의 `pub const`로 생성한다 (`rerun-if-changed`). `common::paths`로 노출한다.
3. Python: 생성기가 `cores/python/src/skim_search/__init__.py`의 생성 영역에 문자열 상수를 쓴다. `ROOT`는 고정 깊이로 1회 계산하고 값은 `ROOT + "/..."` 문자열 연결로 만든다. `pathlib`·`os.path` import 없음. 사용은 `from skim_search import KEY`.
4. 흩어진 경로 계산(`parents[N]`, `HERE`, config의 `third_party`, `CORES / "target"` 등)을 SSOT 상수로 바꾼다. `CARGO_TARGET_DIR` 같은 환경변수 덮어쓰기는 사용하는 쪽에서 1회 확인한다.
5. 생성기를 `scripts\test.cmd`와 one-shot CI 첫 단계에서 실행한다.

# actual result
미구현. 측정 (Python 3.13, 새 프로세스 15~21회 중앙값, 패키지 로드 기준선 대비 추가 비용):
- 키 42개: `__init__.py` 상수 +14~27µs, 별도 모듈 `paths.py` +198µs, ini 실행 중 파싱 +129~158µs, 접근 약 10ns.
- 키 1,000개: 상수 +303µs, 접근 시 계산(`__getattr__`) +290µs, ini 파싱 +391µs.
- 키 5,000개: 상수 +1,481µs, `__getattr__` +1,344µs, ini 파싱 +1,332µs (키당 약 0.3µs, 방식 무관).
- `pathlib` import 11~12ms. 프로세스 시작: `uv run` 82ms, venv python 직접 56~58ms, `-S` 45ms.

# expected result
- 경로를 정의하는 곳은 `cores/common/paths.ini` 하나다. Rust·Python 코드에 저장소 구조 경로 문자열이나 `parents[N]` 계산이 남아 있지 않다.
- Rust: 경로 상수가 컴파일 상수(`const &str`)이고 실행 중 파일 읽기가 없다. `paths.ini`를 바꾸면 다음 `cargo build`에 자동 반영된다.
- Python: 별도 경로 모듈이 없다. `__init__.py` 생성 영역 밖에 import가 없고, 경로 때문에 추가된 패키지 로드 비용이 기준선 대비 50µs 이하다(측정 기록).
- 같은 키에 대해 Rust와 Python이 같은 경로를 낸다는 테스트가 PASS한다.
- `paths.ini`와 커밋된 `__init__.py` 생성 영역이 다르면 실패하는 테스트가 있다.
- 생성 결과와 exe에 절대경로·로컬 사용자 경로가 들어가지 않는다 (상대경로만, 절대경로는 실행 중 조합). `security_policy` exit 0.
- 키가 200개를 넘으면 생성기가 경고한다 (구조 재검토 시점).
- 측정 결과(import 비용, 접근 비용)를 `ref/actual/logs/paths-bench.log`에 기록한다.
