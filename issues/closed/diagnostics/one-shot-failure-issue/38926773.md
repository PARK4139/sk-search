# title
Keep the one-shot failure SSOT by creating/updating a single backlog issue automatically on failure

# pre-condition
- Git repository with the one-shot pipeline and independent stage entry points
- Reproduce normal runs, stage failures, timeouts, repeated failures and issue save failures in temporary repositories.
- Verify without committing, deploying or pushing the real user repository.

# steps
Source: user request (2026-10-01): no failure.json, the issue alone is the failure SSOT; on failure write only to backlog, after the fix move the same file to closed
1. Reproduce failures and timeouts of settings, commit, classification, CI (build/test/checks), CD and security checks.
2. Confirm the pipeline stops, a backlog issue is created automatically and registered in the priority list.
3. Trigger the same full SHA, stage and failure item again and confirm the active issue is updated without duplicates.
4. Verify nested calls, concurrent failures, failures before the SHA is known, and issue save failures.
5. After the fix is verified, move the same UUID file to closed and remove the active priority row.

# actual result
PASS (2026-10-02).
- Implementation: `cores/scripts/one_shot/failure_issue.py` + `report_failure` in `pipeline.main()`. `failure.json` removed. Only the outermost process records (nested stages only print `FAIL:`) → no duplicates from the wrapper chain. It follows nested `FAIL:` lines to the command that actually failed (`command-*.stderr/stdout.log`) and summarizes its last 20 lines, masked. `Run.command` messages distinguish `command timed out` / `command failed ... (exit N)`.
- Key `sha | stage | item`: the item is normalized by removing command IDs, SHAs and absolute directories. The next run commits the previous failure issue, which changes the SHA, so if two SHAs differ only in `issues/` and `ref/actual/` they count as the same source and the existing issue is updated (found during implementation: at first every run created a new issue → fixed).
- Concurrent writes are serialized by `ref/actual/logs/one-shot/.failure-issue.lock`. IDs come from `issue_ids.get_issue_id()`.
- Verification `test_pipeline` 25/25 PASS (`ref/actual/logs/one-shot-pipeline-tests.log`), 4 new:
  - CI failure (exit code 3) → one issue and one priority row, account name and token masked, no failure.json → a repeated failure on the same source adds one recurrence line to the same file, no new file or row.
  - Settings error (before the SHA is known) → SHA recorded as unknown with the reason "failed before the commit stage", stage=setup. Issue cannot be saved (path blocked) → prints `failure issue not saved`, keeps `FAIL:`, exit 1.
  - 4 concurrent records → 1 created, 3 recurrences. After moving to closed, a recurrence creates a new backlog issue linking the previous record in `issues/closed/...`; the closed file is unchanged.
  - Classification: timeout / exit code N / not runnable / check failed, item normalization.
- Docs: exception in `rules/issue.md#incidents`, `rules/one-shot.md#failure-issues`.
- Prerequisite implemented: per user instruction (2026-10-01), get_issue_id() in cores/scripts/issue_ids.py and a single issue_ids.sqlite3 in the Git common directory became the ID allocation SSOT. Existing issues and reservations are imported only once; afterwards IDs are allocated by index and transaction. Automatic failure issues use this API. Duplicates between separate clones are checked before merging.
- 7 ID tests PASS: regeneration on collisions with existing issues/reservations, concurrent contention for the same candidate, 32 separate processes and restart, detection of existing duplicates, reservation kept when logging fails, import of earlier reservations without rescans, single DB and speed measurement. Evidence: ref/actual/logs/issue-id-tests.log. 200 API calls: p50 5883.4 us, p95 6890.0 us, max 151477.8 us (including persistence and logging, excluding Python start and first initialization). Evidence: ref/actual/logs/issue-id-bench.json. This result alone does not complete the automatic failure issue feature.
- Verification tool incident and action: an unclosed SQLite test connection made temporary DB cleanup fail once with WinError 32, because the sqlite3 connection context manager only commits/rolls back and does not close. Closing explicitly with contextlib.closing, all 7 re-verified PASS. Prevention: tests also make DB connection lifetimes explicit.

# expected result
- On failure, later stages stop and the run exits abnormally. No separate failure summary or state artifact such as failure.json is created; the single issue is the SSOT for the failure, its judgment and actions. Original run logs are kept as evidence and linked from the issue.
- The first failure is created as issues/backlog/diagnostics/one-shot-failure/{uuid:8}.md with the standard template. No separate closed record is written. It is registered in issues/priority.md.
- The issue records failing stage and item, full SHA, run ID and time, exit code or timeout / not runnable, reproduction command, masked error summary, evidence log paths, and cause / action / re-verification history. Unconfirmed causes are written as Unconfirmed; an unknown SHA states the reason.
- An active backlog/working issue with the same SHA, stage and failure item gets a recurrence entry. Nested pipeline / independent stage calls and concurrent failures cause no duplicate files, priority rows or damage to existing history. Closed issues are not reopened; a recurrence creates a new backlog issue that links them.
- After the fix is verified, the same UUID file moves to closed and the priority row is removed. No closed file is created at failure time.
- Secrets and personal paths in issue records are masked. If the issue cannot be saved, the error is printed and the original failure stands (abnormal exit), with no separate failure artifact for it.
- The implementation adds the single-issue exception for one-shot failures to rules/issue.md#incidents, referenced from rules/one-shot.md. PASS/FAIL verification and run evidence for automatic creation, deduplication, stopping, masking and save failure are saved to files.
