- Verdict: measurement and report PASS. Peaks over the target are recorded, not hidden.
- Added (2026-10-01 20:2x): distribution of 30 runs with 1 ms timer resolution (`timeBeginPeriod(1)`) — first result p50 49.6 ms, p90 53.6 ms, max 66.4 ms, mean 49.9 ms, over 50 ms 13/30. Search start p50 22.9 ms, max 26.5 ms (over 1/30). Log: `ref/actual/logs/e2e-ui.log` "latency distribution".
- Technical constraint (reported per the handover final request, not changed on our own):
  - Floor ≈ coalescing 20 + run preparation 2.5 + rg process start ~17 (median of standalone measurement 16.6) + sk processing after input ends ~5.6 (fixed regardless of options) ≈ 46 ms. rg start variance from the OS, antivirus etc. (up to ~35 ms) makes the tail.
  - With the rg.exe + sk.exe process model of handover §1, §12 and the "coalescing 20 ms → search" order of §3.1, ≤50 ms cannot be guaranteed reliably.
- Minimal alternative (user decision needed): leading-edge coalescing — search immediately if at least 20 ms passed since the previous search start; batch only consecutive input within 20 ms. Expected first result ≈ 28 ms. This changes the interpretation of the §3.1 flow, so apply only on approval.
