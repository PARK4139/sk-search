# title
Failed one-shot runs consume version numbers, leaving gaps in released versions

# pre-condition
- Shared `3rd_party/skim-search/versions.json` (full SHA ↔ version assignments)
- The usual flow of rerunning with a fix commit after a failure (the failed SHA is never used again)

# steps
Source: user request (2026-10-02): failed one-shot runs also consume a version each / rules/one-shot.md#versioning
1. Make a change and run `scripts\one-shot.cmd --bump patch` → CI fails
2. Commit a fix and run again → success and push
3. Compare `versions.json` with what is published in `3rd_party/skim-search/{SHA}/`

# actual result
PASS (2026-10-02, commit eca81fc).
- Implementation (`pipeline.py`): assignments are recorded as `status: reserved` (+ top-level one-shot PID and run_id); after the push is verified `release_version()` finalizes them as `released` (+released_at). Next number = bump(highest of `released` versions and reservations of running runs). Reservations of other SHAs whose PID ended become `superseded` (+superseded_at, `package_published`) and their number is reused. The same SHA reuses its reservation. The classification base is the last `released` SHA. Existing entries without `status` count as `released`. The top-level PID reaches stage child processes through `SKIM_ONE_SHOT_PID`.
- Decision different from the expected result: instead of "fail on conflict with a running reservation", a running reservation makes the run take the next number (concurrent runs do not fail needlessly; different SHAs still never share a number). If one of two concurrent runs fails, only that number stays empty (rare).
- Verification `test_pipeline` 29/29, all Python 42 OK:
  - Failed run (process ended, not pushed) then new SHA → same 0.1.1 assigned, failed entry `superseded`, after release the next minor → 0.2.0 (no gap).
  - Retry of the same SHA → same reservation reused; a released version is never reused (next 0.1.2).
  - A running reservation is not reused (0.1.2); concurrent assignment stays unique.
  - Old-format entries → treated as `released`, next 0.3.5 and base = that SHA.
  - Full wrapper push → `released`, `--stop-after security` → stays `reserved`.
- Real run: one-shot run `20261002-091449-5d3dbe35` — `version_assigned` 0.6.2 (base 88bf2a0, from existing entries) → push → `version_released` 0.6.2, origin/main == eca81fc.
- Docs: `rules/one-shot.md#versioning`.

Previous state:
- The version was assigned in the commit stage and written to `versions.json` permanently right away. Even when CI, CD, security or push failed afterwards the record stayed, and the next SHA got the following number.
- Records 2026-10-01~02: 0.1.1, 0.2.0, 0.2.1, 0.2.2, 0.2.3 never published because CI failed. 0.3.0 was published by CD but blocked in the push stage (security_policy false positive), so it is not on the remote. Actually pushed versions: 0.2.4 → 0.4.0 → 0.5.0 → 0.6.0 → 0.6.1.
- Reusing the version for a retry of the same SHA worked, but after a failure the rerun usually has a new SHA, so only the number was consumed.

# expected result
- A version number is finalized only for runs that succeed through push. Assignments of failed runs are not finalized, and the next run computes from the last **finalized** version. Consecutive pushed versions have no gaps (only normal increments by classification grade).
- Build injection and CD publication still use the assigned version (reserved while running). A retry of the same SHA reuses the same reservation.
- Concurrent runs never give the same finalized number to different SHAs (locking and atomic updates stay). A conflict with a running reservation fails with the reason recorded.
- Packages published under a reservation that was never finalized (e.g. push blocked) are recorded distinguishably (not deleted; the no-overwrite rule stays).
- Compatible with existing `versions.json` records (assigned entries unchanged, only new status fields added). `rules/one-shot.md#versioning` is updated.
- Verification: tests in temporary repositories for no gap after failure → new SHA success, retry after a push failure, same-SHA reuse, concurrent assignment and compatibility with existing records PASS. Evidence in `ref/actual/logs/`.
